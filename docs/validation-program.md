## AIHR 能否生成标准业务用例

**可以生成候选，再用独立业务事实将其晋级为标准用例。**现有扫描读取了 2110 个文件，识别 61 个入口和 239 个去重路由候选；这些是测试范围，不是已执行覆盖。AIHR HEAD 为 `dc781c3` 且工作树有修改，复现必须封存实际工作树快照。

已核对的链路：简历页「立即运行」→ preload/bridge → 网关创建 collection Run → File 上传 → 后处理 worker → 候选人/岗位/评估及计费终态。已有 Go E2E 覆盖创建 Run、上传和读取，未覆盖完整异步终态。

第一批候选覆盖：

- W01/E01/E02：配置页面、Electron 立即运行、登录失效/风险确认。
- R01–R05：PDF 上传终态、client_item_key 幂等、非法文件、瞬时重试、终态失败。
- O01/O02：在线简历、附件接替时的阶段身份。
- M01/B01：手工录入的身份关联、评估重试恰好一次计费。

生成过程复用现有 `inspect_test_scope`、外部 `.proofkit/workflows.yaml`、Charter 和连接器：源码发现链路 → 生成成功/拒绝/重复/重试情景 → 领域审阅预期 → 合成 fixture → 独立 Oracle → 初态重置和清理 → 三次真实重复。测试工作区放在 AIHR 仓库之外。

晋级前必须具备隔离、可重建的部署和测试租户；Run/File/Candidate/Job/Assessment 身份从本次动作关联，不能借用历史成功；终态和账务由网关/账务独立读数确认。真实平台采集需隔离账号或受控适配器，并在成绩里标明覆盖边界。

再单独加入已知缺陷及修复前后副本，计算缺陷召回、误报、证据完整率和修复回归。公开任务完成率不能替代这些指标；没有足够独立读数时给出 inconclusive，不凭 UI 文案确认 Bug。

每条标准用例须封存：自然语言任务、需求来源与版本、初态/合成数据、允许副作用、预期业务不变量、独立判定器、期限、清理和证据要求。先验证正确版本可通过，再验证已知错误版本会失败；任务执行侧不接触缺陷位置和判分答案。缺陷副本只在独立测试部署制造，不修改用户当前 AIHR 工作树。

首批缺陷候选围绕重复提交产生重复业务结果、异步失败却显示成功、重试重复扣费和错误岗位关联。它们是待领域确认的验收情景，**不是已经发现的 AIHR Bug**。盲测分别报告 `召回=正确发现的缺陷/已植入缺陷`、`精确率=经确认的有效报告/全部 Bug 报告`；正确版本上的错误 Bug 报告另计误报，未判定用例单列。修复建议需绑定相关源码、失败事实和修复后回归证据，不能仅以模型解释是否合理评分。

## 失败分析与增强闭环

分别记录「观察阶段」「调查信号」「根因及确认状态」。分类包括环境/宿主、MCP 契约、定位/动作、规划/超时、证据/提交、答案/业务结果、评判器疑义；一题可有多信号。报告不复制标准答案、请求正文或页面原文。

每个改进项必须有：失败输入及证据哈希 → 最小复现 → 能力归属 → 修改依据 → 同题及同类回归 → 完整固定集比较 → 新失败检查。只有 trace、HAR、独立状态及受控重跑支持时才确认根因。

| 观察到的问题 | 首先核查的能力/模块 | 根因确认所需事实 |
| --- | --- | --- |
| 环境未就绪、宿主重连 | 环境控制、宿主连接与恢复 | 启动/重置读回、时间线；重连本身不证明任务失败原因 |
| RPC 拒绝或无效参数 | contracts、MCP、宿主使用指引 | 可重放请求的结构、契约版本；不得把业务失败归成 RPC 成功 |
| 歧义定位、控件不支持 | Web/Electron Adapter、页面观察 | 失败步、当时控件状态、真实正负例最小复现 |
| 循环探索、超时 | 宿主规划、会话连续性与 Runner | 每阶段耗时、无进展动作和恢复轨迹；不能仅凭总耗时归因 |
| 缺 HAR/独立读数 | Observer、Evidence、提交审计 | 必需事件的录制范围、哈希、任务身份与判定规则校准 |
| 答案错、业务终态错 | 宿主推理、Charter、Oracle、被测产品 | UI/动作事实与独立事实比较；确认是漏测、误判还是产品缺陷 |
| 正确操作也被拒绝 | 评判器/数据集 | 独立成功正例、明确失败负例和版本一致性 |

现有诊断器已提供读取/导航/修改三组统计、失败阶段、多调查信号和轨迹哈希检查；上述更细能力归属仍需证据复核，不能自动宣布某模块就是根因。报告首页应只呈现成功/失败/未判定、能力组短板、恢复/新失败/持续失败、耗时成本和下一步；逐题展开证据与修改依据。完整原始证据留在受控目录。

增强后先跑最小复现及同类正负例，再跑失败题和完整固定集三轮，最后跑未见保留集。修复前后都保留每题成绩及超时，不删除失败或只挑最好一轮；优先修复被独立复现的高影响能力缺口，样本少的能力组标为证据不足。模型/提示/工具同时变化时只能报告组合结果，不能归功于某个代码修复。

下一步按优先级执行：

1. **结果核验优先。** 复核 0/11/108 的筛选、分页和答案投影；453/679 必须核对实际动作请求、HAR 和独立修改后状态，并完成评判规则 UI 正例校准。页面可见、Mission 通过都不足以代替独立业务结果；不添加基准答案特判。
2. **控件与错误证据。** 已新增原生 `selectOption` / `setChecked`，真实 Chrome/Electron 正负例通过；004 未证明总体改善。本次补齐 `selectOptions` 完整集合替换/清空、先校验后派发和精确读回，并扩展现有 `SurfaceControl` 的原生状态计数与动作提示；不据此宣布 108 根因已解决或官方成绩提高。扩展现有 response-gap 证据，区分定位、等待、执行阶段的稳定错误代码，避免 `runner-operation-unverified` 混淆原因；不暴露原始异常文本。
3. **减少无效往返。** 对已核验的依赖动作复用多步 Charter，保留逐步回执、读回、取消与最终独立 Oracle；普通独立启动的 Web Run 不共享页面状态，只有既有 CDP 附加或任务上下文所有者可保持会话。观察循环进度，不能把所有长耗时都归咎于模型或工具。
4. **同条件回归。** 封存模型 ID、CLI、提示/Skill/MCP/浏览器/代码版本、预算及初态；6 个未通过项至少 3 次，再跑完整 12 题 3 轮及未见题。没有同等条件不直接宣称提升。24 候选先独立校准，MiniWoB 控制器与奖励隔离完成后再测。
5. **分离基线。** 同宿主直接 Playwright 与 ProofKit 使用相同题、初态、预算和试验次数，比较成功、摩擦、耗时、成本及证据充分度；AIHR 候选晋级和缺陷召回/误报另设门槛。
